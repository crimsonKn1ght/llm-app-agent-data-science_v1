# Backend Architecture

## Purpose

This repository contains the PatientPlus backend API. It provides
authentication/session handling, user administration, persona/geography/
data-source metadata, prompt template retrieval, and chat history/search
endpoints for an LLM-enabled frontend experience.

The application is built around:

- FastAPI for HTTP routing and middleware.
- SQLAlchemy ORM with pyodbc for Microsoft SQL Server.
- Azure Key Vault for runtime secrets.
- PingFederate OAuth tokens for user authentication.
- Azure DevOps, Docker, and AKS deployment assets under `linked_services`.

## Entry Point

[main.py](../main.py) creates the FastAPI app and owns the process-level
startup behavior.

Key responsibilities:

1. Define the FastAPI lifespan handler.
2. Initialize the SQL Server connection through `BaseModelBuilder.init()`.
3. Start background prompt synchronization.
4. Pre-warm auth secrets in the background.
5. Register health/readiness endpoints before authentication middleware.
6. Attach `auth_middleware`.
7. Dynamically register business routers through `register_routes(app)`.
8. Configure CORS from `settings.URL_ALLOWED_ORIGINS`.

The health endpoints are deliberately registered before auth middleware so
Kubernetes and gateway probes can always get an unauthenticated response:

- `GET /health`
- `GET /ready`
- `GET /healthcheck`
- `GET /api/health`
- `GET /api/ready`
- `GET /api/healthcheck`

## Startup Sequence

```text
Process starts
  |
  v
settings.py loads non-secret env values from project .env / environment
  |
  v
FastAPI lifespan begins
  |
  v
BaseModelBuilder.init()
  |
  v
VaultHandler.get_secret(sql-server, sqldb-name, sql-user, sql-pwd)
  |
  v
SQLAlchemy engine and sessionmaker are created
  |
  +--> background thread: sync prompt files into app_prompt_templates
  |
  +--> background thread: pre-fetch Ping/JWT auth secrets
  |
  v
App accepts requests
```

Database initialization is fail-fast. If SQL secrets or the SQL connection
cannot be initialized, startup raises and the container should restart
rather than accepting traffic in a broken state.

Prompt sync and auth secret pre-warming are non-fatal background work. Probe
endpoints are not blocked by these tasks.

## Dynamic Router Loading

[router_loader.py](../router_loader.py) scans `app/api/**/router.py`. Each
file must expose a variable named `router` that is an `APIRouter`.

The path below `app/api` becomes the URL prefix:

```text
app/api/auth/router.py          -> /api/auth
app/api/chat/router.py          -> /api/chat
app/api/query/router.py         -> /api/query
app/api/prompts/router.py       -> /api/prompts
app/api/admin/router.py         -> /api/admin
app/api/admin/users/router.py   -> /api/admin/users
```

This means new route groups can be added without editing `main.py`, as long
as the file is named `router.py` and defines an `APIRouter` named `router`.

## Request Flow

```text
Client request
  |
  v
FastAPI middleware stack
  |
  v
auth_middleware
  |
  +--> public route? continue without auth
  |
  +--> protected route:
            read access_token from cookie or Authorization header
            decode JWT without signature verification
            extract sub claim as MUD ID
            verify active user in SQL Server
            attach user context to request.state
            refresh token if near expiry
  |
  v
Route handler under app/api
  |
  v
Builder class under app/models
  |
  v
SQLAlchemy session
  |
  v
Microsoft SQL Server
```

Route handlers rely on `request.state.user_id`, `request.state.user_name`,
and `request.state.user_email` after authentication. Public auth endpoints
such as `/api/auth/oauth_verify` are exempt from middleware auth.

## Authentication Components

The main authentication pieces are:

- [app/api/auth/router.py](../app/api/auth/router.py): login/token exchange,
`/me`, silent SSO validation, logout, refresh-token lookup.
- [app/middlewares/auth_middleware.py](../app/middlewares/auth_middleware.py)
: validates protected requests and refreshes expiring access tokens.
- [app/utils/security.py](../app/utils/security.py): helper functions for
token encryption/decryption and JWT decoding.
- [app/utils/cache.py](../app/utils/cache.py): small in-memory TTL cache for
`/me` user data.
- [app/models/users.py](../app/models/users.py): user lookups and admin user
operations.
- [app/models/user_sessions.py](../app/models/user_sessions.py): stores
refresh tokens in `uam_users_sessions`.

Current implementation note: encryption helpers exist in `security.py`, but
the live auth routes and middleware have encryption/decryption calls
commented out. The current cookie value is the access token itself, stored
in an HttpOnly, Secure, SameSite=None cookie.

## Database Layer

[app/models/base_model.py](../app/models/base_model.py) owns the SQLAlchemy
engine, session factory, shared UUID handling, and row serialization helper.

Important elements:

- `BaseModelBuilder._Base`: shared SQLAlchemy declarative base.
- `BaseModelBuilder.init()`: reads SQL connection secrets from Key Vault and
builds the engine.
- `BaseModelBuilder.session()`: returns a SQLAlchemy session; if the session
factory is unavailable, it attempts to rebuild it.
- `MS_UUID`: maps SQL Server `UNIQUEIDENTIFIER` values to Python `uuid.UUID`.
- `row_to_dict()`: converts ORM and SQLAlchemy mapping rows into JSON-safe
dictionaries.

[app/db/database.py](../app/db/database.py) exposes:

- `Base`: the shared declarative base used by models.
- `AuditBase`: common audit and soft-delete columns for most reference and
UAM tables.

Most model files contain:

- A SQLAlchemy ORM model class mapping to a table.
- A builder class that encapsulates query/insert/update methods and session
lifecycle.

## Prompt Template Flow

Prompt text files live in [prompts](../prompts). At startup, [scripts/
sync_prompts.py](../scripts/sync_prompts.py) runs in a background thread:

1. Reads `*.prompt` files.
2. Compares each file's MD5 hash with the latest active database prompt text.
3. If unchanged, skips it.
4. If changed, deactivates prior rows for that prompt name and inserts a new
version.
5. Commits changes to `app_prompt_templates`.

The API retrieves active prompt text through [app/api/prompts/router.py](../
app/api/prompts/router.py) and [app/models/prompt_template.py](../app/models/
prompt_template.py).

## Main Runtime Boundaries

```text
main.py
    owns app startup, middleware, health routes, CORS, dynamic route
    registration

router_loader.py
    owns filesystem-based API discovery

app/api/*
    owns HTTP request/response behavior

app/middlewares/*
    owns cross-cutting request authentication

app/models/*
    owns ORM mappings and database access

app/utils/*
    owns reusable infrastructure helpers

scripts/*
    owns startup/maintenance scripts

linked_services/*
    owns CI/CD and AKS deployment configuration
```
