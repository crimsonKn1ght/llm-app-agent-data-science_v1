## Role In The Backend

This component authenticates users, exchanges OAuth codes for tokens,
validates active users against the database, stores refresh tokens,
refreshes near-expiry access tokens, and exposes current-user
information for the frontend.

The backend uses PingFederate-issued tokens. The user identity comes
from the JWT `sub` claim, treated as the user's MUD ID.

## Public Auth Routes

All `/api/auth` routes bypass `auth_middleware` because `/api/auth` is
listed in `PUBLIC_PATH_PREFIXES`.

Main endpoints in [app/api/auth/router.py](../../app/api/auth/router.py):

```text
POST /api/auth/oauth_verify
GET  /api/auth/me
POST /api/auth/validate_token
GET  /api/auth/get_refresh_token
GET  /api/auth/logout
```

## OAuth Verification Flow

`POST /api/auth/oauth_verify` completes the authorization-code-with-PKCE
flow.

High-level flow:

```text
Frontend sends code, codeVerifier, redirectUri
  |
  v
Backend loads Ping token URL/client secrets from Key Vault cache
  |
  v
Backend posts authorization_code grant to PingFederate
  |
  v
Backend decodes returned access token without signature verification
  |
  v
sub claim becomes mud_id
  |
  v
UserBuilder.fetch_by_mud_id verifies the user is active
  |
  v
Refresh token is inserted/updated in uam_users_sessions
  |
  v
access_token cookie is set
```

Current implementation note: the code comments still mention encrypted
cookies, but encryption is commented out. The current cookie value is
the access token itself.

## Silent SSO Flow

`POST /api/auth/validate_token` accepts an access token and optional
refresh token from a Next.js Silent SSO flow.

It:

- Decodes and validates the JWT through `decode_and_validate_jwt`.
- Extracts the `sub` claim as MUD ID.
- Confirms the user exists and is active.
- Stores the refresh token when one is provided.
- Sets an `access_token` HttpOnly cookie.
- Returns basic user details.

`decode_and_validate_jwt` can optionally verify signatures if a Ping
public certificate is available, but the default call path uses
`verify_signature=False`.

## Request Auth Middleware

[app/middlewares/auth_middleware.py](../../app/middlewares/auth_middleware.py) protects all non-public routes.

It:

1. Reads `access_token` from cookie first, then `Authorization: Bearer`.
2. URL-decodes and strips surrounding quotes from the token.
3. Decodes the JWT without signature or expiry verification.
4. Reads the `sub` claim.
5. Fetches the active user from SQL Server.
6. Attaches user context to `request.state`.
7. Refreshes the access token when it has less than 15 minutes remaining.
8. Sets a replacement cookie when refresh succeeds.

The attached request state fields are:

```text
request.state.user_id
request.state.user_name
request.state.user_email
```

Route handlers should read these fields rather than re-parsing the token.

## Token Refresh

`refresh_access_token(mud_id)` reads the stored refresh token from
`uam_users_sessions`, then sends a refresh-token grant to PingFederate.

If PingFederate returns a new refresh token, the database session record
is updated. The middleware sets the new access token in the response
cookie.

The middleware does not fail the original request only because refresh
returns `None`; it continues unless an authentication error or
unexpected exception is raised.

## Auth Secret Caching

Auth secrets are used often enough that the code caches them in-process.

[app/api/auth/router.py](../../app/api/auth/router.py):

- Uses `_secrets_cache`.
- Populated by `warm_secrets()`.
- Warmed in a background thread during app startup.

[app/middlewares/auth_middleware.py](../../app/middlewares/auth_middleware.py):

- Uses `_secrets_cache` plus `_secrets_cache_time`.
- TTL is 50 minutes.
- If Key Vault is temporarily unavailable and prior values exist, it
  keeps using the cached values.

## User Cache

[app/utils/cache.py](../../app/utils/cache.py) defines `UserCache`, a
thread-safe in-memory TTL cache.

The `/api/auth/me` endpoint uses this cache to avoid repeated joined
user/persona/geography lookups. Default TTL is 300 seconds.

This cache is per-process. In AKS with multiple pods or workers, each
process has its own cache.

## Session Persistence

Refresh tokens are stored in `uam_users_sessions` through
`UsersSessionsBuilder`.

Important fields:

```text
mud_id
session_token
last_logged_at
created_at
updated_at
```

The access token itself is not stored in SQL Server by the current code.

## When To Touch This Component

Change this component when you need to:

- Modify OAuth or Silent SSO behavior.
- Change cookie settings.
- Add signature verification.
- Change token refresh timing.
- Add user context fields.
- Change session persistence.
- Tighten route authorization beyond simple active-user checks.
