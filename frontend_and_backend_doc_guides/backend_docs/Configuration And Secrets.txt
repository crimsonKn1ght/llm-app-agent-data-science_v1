# Configuration And Secrets

## Configuration Sources

The backend separates non-secret configuration from secrets.

Non-secret settings are loaded by [settings.py](../settings.py) using `pydantic-settings`. The `.env` path comes from [app/utils/setup.py](../app/utils/setup.py), which resolves the project root using an absolute path so Uvicorn subprocesses are not sensitive to the current working directory.

Required settings:

```text
AZURE_KEY_VAULT_URL=<full vault URL>
URL_ALLOWED_ORIGINS=<comma-separated frontend origins>
```

`settings.py` currently allows extra environment values but only declares these two required fields.

## Azure Key Vault Helper

[app/utils/vault.py](../app/utils/vault.py) defines `VaultHandler`, a thread-safe singleton around Azure Key Vault SecretClient.

Credential behavior:

1. Try `DefaultAzureCredential`,
2. Confirm it can issue a token for `https://vault.azure.net/.default`.
3. If `DefaultAzureCredential` is unavailable, fall back to `AzureCliCredential`.

This supports two common modes:

- Deployed AKS: Azure Workload Identity through `DefaultAzureCredential`.
- Local development: Azure CLI login through `AzureCliCredential`.

The Key Vault client is initialized lazily on first secret lookup and reused between calls. If a secret lookup fails, `get_secret()` clears the client and retries once to recover from expired Azure credentials.

## Secret Name Normalization

`VaultHandler.get_secret(secret_name)` normalizes names in two ways:

```text
Key Vault name:      secret_name.replace("_", "-")
Environment name:    secret_name.replace("-", "_").upper()
```

Examples:

```text
VaultHandler.get_secret("sql-server")
  Key Vault: sql-server
  Env var:   SQL_SERVER

VaultHandler.get_secret("ping_oauth_secret")
  Key Vault: ping-oauth-secret
  Env var:   PING_OAUTH_SECRET
```

Resolution order:

1. Azure Key Vault.
2. Environment variable fallback.
3. Raise `RuntimeError`.

The environment variable fallback is useful for local development or emergency testing, but secrets should normally be stored in Azure Key Vault.

## Secrets Used By Database Startup

[app/models/base_model.py](../app/models/base_model.py) fetches these secrets during `BaseModelBuilder.init()`:

```text
sql-server
sqldb-name
sql-user
sql-pwd
```

````

These are used to build the SQLAlchemy URL:

```text
mssql+pyodbc://<sql-user>:<sql-pwd>@<sql-server>/<sqldb-name>?driver=<detected driver>&Connection+Timeout=10&timeout=10
```

The ODBC driver is selected from locally installed drivers where the driver name contains both `ODBC` and `SQL Server`.

## Secrets Used By Authentication

Auth code reads these secrets:

```text
jwt-secret
ping-oauth-token-url
ping-oauth-client-id
ping-oauth-secret
```

Primary consumers:

- [app/api/auth/router.py](../app/api/auth/router.py) uses the Ping OAuth token URL, client ID, and client secret to exchange authorization codes and to support silent SSO validation.
- [app/middlewares/auth_middleware.py](../app/middlewares/auth_middleware.py) uses the same Ping secrets to refresh expiring tokens.
- [app/utils/security.py](../app/utils/security.py) uses `jwt-secret` to derive a Fernet encryption key, although encryption is not currently active in the live auth path.

## Auth Secret Caching

There are two auth secret caches in the current code:

- `app/api/auth/router.py` has a module-level cache populated by `warm_secrets()`.
- `app/middlewares/auth_middleware.py` has a timed cache with a 50-minute TTL.

`main.py` starts a background thread to call `warm_secrets()` so the first `/api/auth/oauth_verify` request does not wait for several sequential Key Vault round trips.

The middleware cache is deliberately time-bound. The comments explain that a permanent `lru_cache` can become stale after Azure credential expiry. If Key Vault is temporarily unreachable and the cache already has values, the middleware continues using the last known good values.

## CORS Configuration

`main.py` parses `settings.URL_ALLOWED_ORIGINS` as a comma-separated list:

```python
origins = [o.strip() for o in settings.URL_ALLOWED_ORIGINS.split(",")]
```

These origins are passed to FastAPI `CORSMiddleware` with:

```text
allow_credentials=True
allow_methods=["*"]
allow_headers=["*"]
```

Because cookies are used for auth, frontend origins must be explicitly listed and cookie settings must remain compatible with cross-site requests.

## Local Development Checklist

1. Install dependencies from `requirements.txt`.
2. Ensure a SQL Server ODBC driver is installed.
3. Authenticate to Azure locally with `az login`, or provide environment variable fallbacks.
4. Create a root `.env` with `AZURE_KEY_VAULT_URL` and `URL_ALLOWED_ORIGINS`.
5. Start with `uvicorn main:app --reload --host 0.0.0.0 --port 8000`.

## Deployed Environment Checklist

1. Provide `AZURE_KEY_VAULT_URL` and `URL_ALLOWED_ORIGINS` through the deployment config map/environment.
2. Ensure the pod's service account is configured for Azure Workload Identity.
3. Ensure the managed identity has permission to read secrets from the configured Key Vault.
4. Ensure SQL Server firewall/network rules allow the AKS workload to connect.
5. Ensure ODBC Driver 18 is installed in the runtime image.
````
